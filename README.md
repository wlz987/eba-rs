# eba-rs workspace

进程内、单写者、合作式 EBA 运行时的 Rust 实现，与 `eba-py` / `eba-ts` 语义对齐。

## 两个平级项目

`eba-rs` 与 `eba-rs-infra` 是两个**平级且互相独立**的项目，都是 `eba-py` 的复刻，面向不同目标环境：

- `eba-rs-infra`：面向裸机 / 系统编程（如撰写操作系统）。`no_std` 核心（默认特性下带 `std` / `uuid` 扩展），使用 `spin` 锁与 `alloc` 集合，无 tokio / 运行时依赖，由调用方在裸机上手动驱动运行时。模块与 `eba-rs` 同构：Envelope、模式匹配、时间、通知、邮箱、请求簿、Job 宿主、协作式运行时。
- `eba-rs`：面向一般开发用户。`std` 实现，承载相同的 EBA 核心语义，并提供基于 tokio 的 `Drive` 异步驱动器。

两者互不依赖（见 `cargo tree`），各自独立发布。

## 测试

```bash
cargo test --workspace
```

- `eba-rs-infra/tests`：与 `eba-rs/tests` 同名同条，逐条人工镜像——只换 crate 名（`eba_rs` → `eba_rs_infra`）。带 tokio 与 `Drive` 的那五本不进 `no_std` 侧：`drive.rs`、`drive_exit.rs`、`recovery.rs`、`wake_token.rs`、`fuzz_drive.rs`（54 本对 49 本）；`denials.rs` 在 `no_std` 侧少五条，那五条全是 Drive 的门，留在 `eba-rs`。判据不同的只有两处，两本文件头各自写明：`shapes.rs` 里 `err_payload` 收 `BTreeMap`（`no_std` 没有 `HashMap`），`cost.rs` 里 `sleep_is_only_ever_a_yield` 在这边数「一处 `sleep(` 都不许出现」，那边数「`sleep(` 的参数里不许有字面量时长」。

## 校验

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets
cargo test --workspace
cargo build -p eba-rs-infra --no-default-features
```

最后一条不许跳：`eba-rs-infra/src` 与 `eba-rs/src` 同源，sed 只换 crate 名，`std::` 要一并换成 `alloc::`/`core::`（`HashMap`/`HashSet` → `BTreeMap`/`BTreeSet`，补一句 `use crate::prelude::*;` 取回 `String`/`Vec`）。这一处换名漏在 `src/mail/bus.rs`、`src/mail/inbox.rs` 上时，默认特性的 `cargo test --workspace` 全绿——只有 `no_std` 那一体会说。

## 与 `eba-py` 的差异

下面引用的 py 条目名以 `eba-py` 某一时刻的 HEAD 为准；py 的册子会改名、也会搬家。如今 `eba-py` 已没有 `tests/`：`b4204ec` 撤走的是 23 本、577 格；更早的 `25f95ff` 把当时那 51 本移到了 tag `hold-412`。所以书名若点到 `test_breach.py`、`test_contract.py` 这类不在 23 本里的册子，指的是 `hold-412` 那一代——两句都还能在 py 的历史里翻到原文，只是没有一个字留在 py 的工作树里。逐条「问不出」的账不在这里，在各测试文件自己那段（`tests/*.rs` 顶部的 `//!`）——两处对不上时，以文件头为准，这一节只讲结构性的那几处差别。

- 原生 `Subscription::close` 不会失败（返回 `bool`），但租约统一走 `Lease` trait：`Bus::wrap_leases` 的观察者交回 `Result<Rc<dyn Lease>, BoxError>`，一次 cover `eba-py` 替换 `Bus.subscribe` 的两种拿法——套一个会失败的包装（`Err` 之前什么都不做），或让这一笔订阅直接失败。要照 py 那样"抛之前什么都没干"，观察者自己先 `sub.close()` 再返回 `Err`：缝在路由建成之后才响，不补这一步就会留下一条没人攥着的路由。因此 `Records::recover`/`retry` 与 `eba-py` 的 `_stuck` 重试队列同构生效——生产路径上它通常无事可做，故障路径上与 `eba-py` 同一条规则。`test_backpressure_park.py::test_a_letter_that_will_not_go_back_is_handed_to_close` 是这条缝的极限：py 把 `pump.restore` 也换成放不回去，逼出「被取出的信回不了箱就当场记进交还名单」那一臂。这边两样都换不动——`restore` 是模块函数，队列也不是会说谎的那只手；而泵在取信之前先问过队列有没有空位，`push` 因此不会失败，`restore` 失败的前置就更够不着：单写者刚刚取走一封信，箱里至多剩 `capacity - 1` 封，放回去一定放得进；「箱子已关掉」那一格，`recv` 早就挡在门外。同一条规则的可见面（交还名单由 `close` 一次带走，半途抛出不清空它）写在 `lifecycle.rs` 与 `drive.rs` 的收尾那几条里。
- `test_faults.py::test_a_failed_delivery_registration_leaves_no_half_group` 要的是「注册『腾出位置就叫我』的那一下炸了」这一臂：`Bus::ready_or_watch` 在这边只做两件都不会失败的事（把 interest 挂上路线轨、挂上空位守候），没有可失败的一步，因此 `Outbox::offer` 没有回滚臂可写——py/TS 那一臂防的是别人的代码在钩子里抛错，这边由签名挡住。同一条规则另两支（`test_fault_lease_wrap::test_failed_subscription_notify_rolls_the_route_back`、`test_lifecycle::test_inbox_close_retries_a_failed_route`）已在上面记着账。
- 投递的三种结局：py 的测试把 `Bus.publish` 换成自己的那一只手，于是同一封信可以有三种下场——照常落地、抛错、或者干脆交回「没人接住」。这边的等价缝是 `Bus::observe_publish`，`PublishVote::{Pass, Silent, Fault}` 一格对一种：`Fault` 是一笔投递失败（进重试预算），`Silent` 不是失败，是没送到（`publish` 就地交回 `Ok(false)`，路由一步都不走）。`test_fault_retain.py::test_a_refused_publish_ends_the_wait_and_keeps_the_letter` 量的正是这一格的分别。
- 帧里记的是句柄不是订阅：py 换掉 `Bus.subscribe` 的那只手会自己补一句 `bus.note_grant(box, handle)`——「这一次订阅交回的句柄是它」。这边的同名接缝 `Bus::note_grant` 因此要求 `GrantFrame` 装 `Rc<dyn Lease>`（原来只装原生 `Rc<Subscription>`）：`Bus::subscribe` 先把原生句柄记进当前帧，`note_grant` 顶掉这只箱子的最后一格；顶掉之后再记第二份，就是 py 的「两个主人」，谁也归不了主。`Lease` 相应多一句 `active() -> Option<bool>`——`None` 就是答不上「我还活着」，与 py 的 `getattr(handle, "active", None)` 同一格。一处换算：py 按 pattern 挑哪一笔订阅下手，这边的缝只交出订阅本身（`Subscription` 不暴露自己的 pattern，克制暴露），`contract_lease.rs` 里两处因此以「第一笔订阅」代替——那一笔正是被挑中的那一条。
- 路由的拆除在这边是全函数：`Receiver::close`、`Routes::detach`、`RouteRevoke` 都不返回 `Result`，`Interest::notify` 也只承诺"叫醒"，不承诺"可能失败"。所以 `test_lifecycle.py::test_inbox_close_retries_a_failed_route` 那种"关箱时有人改口抛错"的把式没有对应写法；留下的那一半（关箱把路由退干净、之后的投递不再进箱）由 `lifecycle.rs` 与 `mail.rs` 承担。
- 同上，`test_fault_lease_wrap.py::test_failed_subscription_notify_rolls_the_route_back` 要的是"叫醒路由的那一刻报错，这一笔路由当场退回去"。这边的钩子是 `Fn()`：能 panic，交不回 `Err`，也没有可捕获的失败让 `subscribe` 倒着走完。规则仍在那儿（`Routes::subscribe` 先改表，再由 `Bus` 叫醒），只是没人能把钩子改成会失败的形状。
- 叫醒不握着借位。py 的 `_Routes.subscribe` 在字典上改完就地 `changes.notify`，重进这张表无所谓；这边的 `RefCell` 会把重进变成 panic。所以 `Routes` 的每一步改动只交回"该叫醒哪个 pattern"，由 `Bus` 放开借位之后再叫醒——`Watchers::notify` 同理，先把守望者取出来再落钩子。`test_subscriber_start.py::test_a_box_that_closes_midway_lets_go_of_the_lease_it_just_made` 就是踩在这道缝上：路由刚建成，钩子就把箱子在订阅者脚下关掉。
- 守望是弱引用握着的：`Watchers` 只留 `Weak<Interest>`，还没落地的 offer 由 `Bus::offers` 撑着，和 py 的 `_offers` 同一形状。撒手的守望者不会被下一次叫醒唤回来（`test_dropped_interest.py` 两条），空位与路由变化都跳过那一格。
- `Runtime` 的状态是私有的，而 `add`/`advance` 全程持有它的可变借用：回调里既读不到 `state`，也没人能从 notify/wake 里再叫一次 `shutdown`。因此 py 的 `test_shutdown_cannot_undo_a_close_underway` 在这边改查它能被观察的那一面（closing 的 Host 不被退回 draining、最后一次 close 走完才 closed），而 `test_shutdown_during_admission_gives_the_route_back`、`test_a_refusal_with_a_stuck_route_reports_both_failures`、`test_shutdown_from_the_wake_that_admission_itself_strikes` 三条只能留在 py/TS：`add_inner` 里那道"中途被人关停就倒着走完"的复查仍然在位，只是这里的借用纪律让测试无法把它踩响。
- `Queue::push` 不说谎：它只在 `size >= capacity` 时交回 `false`。py 把 `core.queue.push` 换成永远不收，是为了把「队列看着还有位子」和「队列就是不要」分成两件事；这边分不开——`pump` 的守卫先拦，`push` 那句因此是纯防御。`test_backpressure_park.py::test_a_refused_queue_puts_the_letter_back_while_a_reply_is_held` 换踩真装满的那一格，后果同一条：信不进队列、不记拒绝、原样留在箱里等回信让开。
- `Drive` 的票据与两段相位旗是私有的：py 直接读 `drive._wake`、拨 `drive._pumping`/`_releasing`，这边由 `wake_token()` 与 `set_phase()` 开一个同形状的最小观察面（和 `waiter_count()` 对应 `drive._waiters` 是同一条路）。`runtime._agenda._wake` 与 `drive._stops`、`drive._delay()` 同样只剩这一条路：`wake_bound()` 问一句叫醒还挂着没有，`stop_count()` 数欠着的取消，`next_delay()` 交回下一口气要停多久（`None` 就是停到被叫醒）。py 数「泵转了几圈」靠子类盖住 `Runtime.advance`（`test_drive.py` 的 `_Laps`）；这边的 `Runtime` 是结构体，没有那条缝，圈数由泵在唯一那个 `advance` 调用点上记一格，`lap_count()` 交回它——同一个量，不是它的代理。
- `test_drive_exit.py` 的三条在 RS 换了形状：第二只泵就是同一只泵重开（`Drive` 独占 `Runtime`，`start()` 把上一轮的 waiters、stops、空位守候一并复位）；`drive._task is None` 那一格由「开不出新信」交出来；`_space_kicks` 不用清——空位那张票的强引用只在泵手里，泵一撒手它就散了。
- 「没人作答的调用」不能拿一只什么都不做的钩子当道具：静默补答（`job_silent`）会抢在收工之前把这一等结掉。`drive_exit.rs` 派的是没人收件也没人撒手的箱子，账上就一直欠着这一笔——与 py/TS 同一条规则，只是这里必须这样造。`kick()` 的守卫与 py 同一条：泵在动手或清算这两段里自己立的旗，不兑一次新的唤醒。
- 一台 `Runtime` 只坐一只泵这条规则，在这里由类型代劳：`Drive::new(runtime)` 收走 `Runtime` 的所有权，第二只泵连构造参数都凑不出来。py 的 `test_second_drive_is_rejected` 那句报错因此在 RS 是结构上不可达的一支——没有第二条路可踩，也就没有对名的断言。（TS 那边 `Runtime` 是引用语义，同一条规则仍由 `Drive` 里的 `WeakMap` 兑现并测出来。）
- 泵的死法只有一种：`abort_pump()`（对应 py 直接掐 `drive._task`）交回的是 tokio 的 abort——协程就地被丢掉，不会先在 `CancelledError` 里走一遍收尾。所以 `cancelled_pump_reports_itself_to_the_drive` 与 `externally_closed_pump_ends_the_drive` 留住了共同的那半条（泵不在了就不许再开新信，等的人也不会被晾着），丢掉的是 py 结局的名字：那边是取消的报错再加一次 `CancelledError`，这边是 `close()` 交回 drive closed。
- 结果账本自己坏掉这一路（py 把 `book.take_result` 换成会抛的）在这里造不出来：`Records::take_result` 只有一句错，`UnreadableResult`，而它是设计好的 keep 分支（对上了号却读不出正文：留下，别打断这一轮），不是意外。`execution.rs` 里那句“把信留给 close、把这一轮停下”因此没人能踩响——`a_broken_result_*` 两条留在 py/TS。
- `shut_door` 的两条腿（Host 在 closing/closed、收件箱已关）在测试里只踩得到状态这一条：`Receiver::close` 归收件人，而收件人在 `Caller` 手里，没有公开接缝能在 Host 还跑着的时候关掉它自己的箱子。py 那只 running 却已关箱的替身因此换成状态的另一侧，判的是同一句“关着的门不再接取消”。
- `Clock::now_ms() -> u64` 不会失败，因此本 crate 没有 `ClockError` 这条路径；`Wake` 的多等待者、`parse_pattern` 在 `Core::new` 里的复用仍是真契约不变量，只在契约被违反时 panic。
- 有些校验在 `eba-py` 里是运行时的，在这里由类型系统承担，因而没有对应的失败测试：负数 `start`（`SeqIdGen::new(u64)`）、非 Envelope 的 `can_publish`、钩子返回协程或非 `None` 值（`JobHooks` 一律返回 `Result<(), BoxError>`，`test_subscriber_start.py::test_a_hook_that_answers_with_a_value_is_refused` 因此没有可写的形状）、工厂返回协程（`MakeJob` 的返回类型就是 `Result<Job, BoxError>`，交不出一只「没启动的协程」，`test_fault_retain.py::test_async_factory_closes_the_rejected_coroutine` 因此没有可写的形状，那边剩下的是 adoption_failed 这一句，已由 `fault_lease.rs` 与 `fault_retain.rs` 各自量过）、`Matchmaker::reply` 收到一个不是结局的 payload（形参就是 `&ResultBody`）。`test_protocol.py` 里还压着六条同样的账：`test_negative_start_rejected`、`test_id_sources_validate_their_start`（`envelope_id`/`actor_id` 收 `impl Into<String>`，`SeqIdGen::new` 收 `u64`，字符串和负数都进不来）、`test_an_actor_id_must_be_a_string_at_every_door`（`Publisher`/`Subscriber` 的形参就是 `ActorId`）、`test_a_clock_that_answers_nothing_is_a_failure`（`Clock` 是 trait，没有一只“读了只会报错”的基类钟）、`test_a_receiver_can_only_be_made_by_an_inbox`（`Receiver` 只能由 `Inbox::receiver` 交出）、`test_a_host_or_a_box_built_without_its_constructor_is_refused`（`Core::new` 是唯一的构造口， trait 对象也没法绕过 `JobHost` 的字段）。`copy_header_only_takes_a_header` 与 `snapshot_freezes_what_it_is_handed` 因此各写下能被观察的那一半：地址过抄手不洗面孔，快照不复制 payload。`reply` 取一个已取出的 `EnvelopeId` 而非 `IdGen`：取 id 由账簿负责，且只在构造出 `Matchmaker` 之后才取，失败不花费 id。
- `test_public_validators.py` 的三条在这里换了量法。`test_id_gen_start` 与 `test_schedule_numbers` 挡的是 bool/float/负数——那些值在 `SeqIdGen::new(u64)`、`Schedule::new(_, Option<u64>)` 上根本说不出口，于是这两条改量剩下会算错的地方：起点到底算不算数（含 `default()` 约定的那一个、id 的 32 位补零），以及期限过期时 `wait_ms` 是钳到 0 还是回绕成天文数字。`test_the_advertised_door_only_opens_what_it_lists` 的前半句（`__all__` 里写着的名字必须真拿得到）由 rustc 代劳——`pub use` 写错或写重一个名字就编不过；后半句仍在：`public_validators.rs` 用 `TypeId` 比对门上与家里的每一个类型，trait 用 `fn(&dyn Door) = takes_home` 这条赋值，函数比 `fn_addr_eq`，常量比值——两条路走进去必须是同一份实现。

- py 的 `eba/job/turn.py` 是一张「谁的轮次」的账：`Runtime.add` 把 Host 登记成自己的，Host 上那些只属于轮次的动词（`bind/unbind/drain/begin_close/close_owned/notice_closed_inbox/take_abandoned/advance/withdraw/project`）动手前先问这张表——不在这张表上、表上站着别人、或拿的不是这一轮钉住的那把钟，一律 `runtime is the only writer`。这一侧没有这张表：这些动作由 `Runtime` 直接拿着 `Core` 的可变借位完成，`JobHost` 上没有那扇门，也就没有可以守卫的入口，"谁是写者"在编阶段就定了。因此 `test_owned_verbs.py` 的 `test_each_owned_verb_refuses_an_unlisted_host`、`test_refused_verbs_left_the_host_untouched` 与 `test_runtime.py` 的 `runtime_is_the_only_writer_after_add`、`advance_refuses_any_clock_but_the_pinned_one`、`the_turn_is_not_a_runtime_attribute`、`overriding_advance_does_not_replace_the_pump`、`a_decorator_on_enter_still_advances` 都没有可写的形状（同一文件里的 `wait_uses_the_observed_instant` 落在 `runtime_job.rs`，`owned_verbs.rs` 落的是收件箱移交那一条）。
- 封存一个作业在 py 是 `from eba.job.ending import seal_job`，这一侧 `seal` 住在 `job::execution`（py 的 ending.py 在这边并进了 execution.rs），只对 crate 内与测试开门，不上根门。`tests/route_roster.py` 读的 `_state(inbox).routes` 同理：箱上的名册是 `Inbox` 的私有格子，这边开一个 `inbox::route_count` 交一眼数出来的值——名册上站的是"哪台 Bus 还替我订着"，不是一笔订阅一格，所以两条 pattern 同一台 Bus 只算一格（py/TS 同一条规则）。

- `test_suite_shape.py` 是对 py 自己的文件布局做的 AST 自检（`if __name__ == "__main__"` 不许夹在类中间）。它盯的是解释器的运行方式，这边没有等价的坑：`cargo test` 按 `#[test]` 收条目，一个文件里的条目不会因为守卫的位置而漏跑。
- `test_ledger.py` 两格量的是 py 自己的量法：`measure/sweep.py` 全树挖一遍，`measure/ledger.py --write` 把还活着的格子连同它们那句原话存成 `measure/alive.json`；`test_the_snapshot_still_describes_this_tree` 问总数还对不对得上，`test_the_snapshot_records_a_sentence_for_every_alive_cell` 问每一处的原话还在不在原处。两句合起来拦的是同一件事——拿旧记录的行号当今天的身份证。这一侧没有这份快照，也没有一台以名字为账的 runner：`cargo test` 的账本就是一函数一格，行号搬家不会让任何一笔账悄悄过期。TS 侧同记这两格。
- `Drive` 拥有它的 `Runtime`（`eba-py` 只是引用一个），所以"泵还在跑时从外面 `shutdown`"在本 crate 不可表达；`Bus` 是可共享句柄，`Clone` 交出的是同一张路由表的另一个视图。
- 钩子与 `Clock` 都拿不到正在跑的 `Runtime`：`advance` 全程持有它的可变借用，`schedule()` / `shutdown()` 只能从外面调。所以 `eba-py` 里那几条"从回调内部旁观、甚至反过来指挥运行时"的测试（`busy_schedule_hides_ready_work`、`clock_observation_cannot_reenter`、`test_contract_host.py::test_a_clock_that_reads_itself_is_cut_short`、`test_contract_host.py::test_reentrant_cancel_is_rejected_and_close_drops_the_wait`、`test_close_host.py::test_shutdown_from_the_factory_that_adopts_the_root`、`test_runtime.py::test_a_standalone_round_cannot_be_reentered`）在这里没有对应写法——被观察者与观察者在同一块内存上，借用检查先拒绝了：钟或工厂伸手去够 `Runtime` 的那一刻，`RefCell` 已经替 `reentrant` 那句判定报了 `AlreadyBorrowed`，闸门轮不到说话。py 的 `Runtime` 是一层薄壳，回调里回头调它既合法也有答案；这边的答案由类型给出，同一条规则（一次只有一只写者）不会被人从钩子里绕开。规则本身仍然生效，`Runtime::schedule` 照旧按 `!busy` 遮蔽。`schedule_during_advance_reuses_the_same_instant` 因此换了个旁观口：钩子里数的是时钟被读了几眼，一轮读完一眼就算复用成功，不必再要那份快照。`blocked_delivery_still_expires_other_jobs` 同理换尺子：py 覆写 `Runtime.advance` 数空转的轮数，这里包一只会数自己的 `Counted` 钟——一次 advance 只认一次时，两把尺子量的是同一件事。
- 快照这一步在这边不存在：`Envelope` 是 `Arc` 后面的不可变值，`make_envelope`/`Header::new` 在门口就把 topic、id、cause 和地址核清楚，取出之后没人能再改它。所以 `test_contract_keep.py::test_a_result_that_cannot_be_snapshotted_is_kept_for_close` 与 `test_a_request_that_cannot_be_snapshotted_is_kept_for_close` 只能留在 py/TS：那边靠 `object.__setattr__` 把已经取出的信改坏，逼出「快照做不成就留给 close，别打断这一轮」这条臂；这边的同一句改写在 `Arc<Envelope>` 上编译不过，`pump` 因此没有可失败的快照可兜。同一份规则的可观察面（对不上号的信不进账、期限仍然说话）由 `contract_keep.rs` 与 `contract.rs` 承担。同一句话也管着 `test_bus.py::test_illegal_envelope_cannot_publish` 与 `test_liveness.py::test_raw_envelope_is_rejected`：py 先造一只字段被改坏的 `Envelope`、或干脆递进一个不像信封的对象，看门口的校验拦不拦；这边的 `publish` 收的是 `&Rc<Envelope>`，而 `Envelope` 只能由 `make_envelope`/`Header::new` 交出来，两种坏都构造不出来——拦下它们的不是那一段 if，是签名。

## 无路由

`Bus::publish` 返回 `Result<bool, BoxError>`，`true` 表示有人接住了这封信。事件与结果没人认领时照常安静落地；request 不同，它欠一个答复。一条没设期限、又谁也没收到的 request，把期限就地记为已过（`time::deadlines::ELAPSED`）：下一步交回空的结局（`Completion::is_timeout`），而不是把等待悬到永远。设了期限的请求仍按期限走，`dependency_timeout` 的语义不变。

因此超时只有一种含义：这封投递成功的信还没等到回音。没人收件不再伪装成"还在等"。`eba-py` 里"路由器不回报就算已投递"的软约束在本 crate 由类型系统承担：回报是 `publish` 签名的一部分，无从省略。`test_contract_route.py::test_a_router_that_does_not_report_keeps_the_wait` 量的正是这一格：py 换掉 `publish`，让它照投不误却不回报——等待因此悬着，`publish` 交回的是「没说没人接」。这边没有「投了但不说」这一种：`Pass` 会走完整条路由，`Silent` 是根本没送到，两者都说话，只是说法不同。
